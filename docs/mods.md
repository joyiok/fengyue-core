# Mod 设计

> 参考 AI风月 的 Mod 机制（**只学机制**：作用域、来源策略、可复用组件。不学它的内容分类法、
> 标签表、文案、样式）。本文是实现前的对齐稿，也是实现时的依据。

## 一、Mod 是什么

**一个可复用的组件，玩家在开一局时加载到某张卡上。** 它是内容，不是插件——它往提示词里加东西，
而不是改程序行为。

一张 Mod 的载荷只有三样：

| 载荷 | 折进哪里 |
|---|---|
| `system` 提示词片段 | 并进 system 块（卡自己的内容**之后**，示例**之前**） |
| `postHistory` 指令片段 | 并进 `post_history_instructions` 那一槽 |
| 世界书词条 | 并进世界书扫描（和卡关联的书合并，`resolveWorldbooks` 已经支持多本合并） |
| `style`（可选 CSS） | 受卡的样式策略约束，见 §四 |

**为什么 system 片段放在卡之后**：Mod 补的是场景/规则/装扮，它扩展设定而不是覆盖设定。卡作者
写的东西是这一局的主体，Mod 是加上去的一层。多个 Mod **按加载顺序**追加。

## 二、两种作用域

| | 什么时候能选到 |
|---|---|
| `shared`（公用） | 任何作品都能选 |
| `dedicated`（专用） | **只有绑定的那一个作品**能选到 |

专用 Mod 是作者给自己的卡写的配套件（「这张卡的隐藏支线」「这套服装」），别人不能把它架到别的卡上。

## 三、可见性

`private` 只有自己能用；`public` 进 **Mod 广场**，别人可以搜到并加载。上传广场是显式的，不是
发布顺带的。

## 四、来源策略（作者对自己的卡说了算）

放在**卡上**（`card.data.extensions.story.mods`），所以它跟着 PNG 走，装到别的站也还成立：

```jsonc
"extensions": {
  "story": {
    "mods": {
      "policy": "own",          // none | own | own-dedicated | all
      "style": "forbid"          // forbid | allow
    }
  }
}
```

| `policy` | 允许加载 |
|---|---|
| `none` | 什么都不许（这张卡就是它自己） |
| `own` | 只有**这张卡的作者自己**创作的 Mod |
| `own-dedicated` | 不许非自己创作的**专用** Mod；公用 Mod 不限 |
| `all` | 全开 |

`style: "forbid"` = 剥掉加载进来的 Mod 的 CSS（「作者禁止加载含内置 CSS 的 Mod」）。

**为什么策略在卡上而不是数据库里**：一张卡被导入到别的安装、被发到广场、被下载——它对自己
「允许被怎么改造」的声明必须跟着它走。存数据库里的话，卡一出门规则就丢了。

## 五、防滥用

1. **来源策略在服务端判**（`POST /chats`），不是在界面上藏按钮。藏按钮只是障眼法。
2. **专用 Mod 只能在绑定作品里加载**，服务端判。
3. **注入面**：Mod *本来就是*提示词内容，这是它的用途。但它由**玩家**选择，所以真正的边界是
   「玩家只能给**允许被改造的卡**加东西」——这就是四档策略存在的理由。`none` / `own` 的卡不会
   被别人的 Mod 动到。
4. **CSS** 是注入面里最脏的一种（可以改整个页面的样子），所以它单独有一条开关，且默认 `forbid`。
5. Mod 广场的举报走现有的举报队列（下一步接）；先不做「按热度自动下架」——那把私怨变成下架工具。

## 六、记账

`mods.uses` 累计加载次数，只是个统计。**不参与计费**——Mod 是内容，不是模型调用。

## 七、Mod 的边界：可以带策略，不能带行为

判据不是「内容 vs 能力」——那条把三件性质完全不同的东西一句话划掉了。判据是：

> **这一层还是不是 `assemblePrompt(card, history, mods) → prompt` 的纯函数？**
> 是 → 它是 Mod。否 → 它是插件。

纯函数这个性质值多少钱：它是全部快照回归的来源。一旦 Mod 能让这一层去调 embedding、去调
外部工作流，那些测试就没了。

| 类型 | 例子 | 判定 |
|---|---|---|
| 纯内容 | 提示词片段、世界书词条、CSS | **Mod** |
| 内容 + 策略 | **记忆 Mod**：摘要指令 + 阈值/长度参数 | **Mod** |
| 行为 | 召回/索引插件、效率工具（外部工作流） | **插件，不做** |

### 记忆 Mod 是 Mod

`MemoryConfig` 本来就长这样：`instruction`（摘要指令——内容）加 `threshold` / `keepRecent` /
`maxSummaryTokens`（策略）。它一一对应，而且摘要是注入进那个纯函数的（`memory: MemoryState`），
纯函数仍然成立。于是两个真实需求现在就该满足：

- 给本来没有记忆区的作品加上记忆
- 「用我这一套摘要风格」——一段可分享的摘要指令

载荷里多一个 `memory` 字段，开一局时覆盖该会话的 `MemoryConfig`。

**但它有一条纯内容 Mod 没有的义务：要计费。** 摘要是一次真实且计费的模型调用（账本里
`…:summary:<upTo>`）。加载一个记忆 Mod 就意味着这个会话会开始为摘要花钱——所以界面必须
写明这一点（「开启摘要，每次合并消耗 N 积分」），纯内容 Mod 不需要这句话。**可见性是接受它
的前提。**

### 为什么召回/效率工具不做

- **召回/索引**：要 embedding + 向量检索，是网络调用，纯函数没了。真要做，先上向量层（M5 里
  也写了：先做向量会花两周调 embedding 而用户感觉不到差别）。
- **效率工具**：外部工作流有副作用、独立计费、还能把数据带出边界。那是插件系统的信任模型，
  不是「加载一段设定」。

## 八、数据形状

```
mods 表（已建）:
  id, owner_id, name, description
  visibility  private | public
  scope       shared  | dedicated
  bound_character_id        -- scope=dedicated 时必填
  system_prompt, post_history   -- 提示词片段
  worldbook                 -- JSON，一组世界书词条
  style                     -- CSS
  memory                    -- JSON，MemoryConfig 覆盖（策略预设，见 §七）
  tags, uses, created_at, updated_at
```

开一局时的选择存在**会话里**（`chat_metadata.story.mods`），所以一份对话记录自己就能说清楚
「这一局装了什么」，跟着 JSONL 走。
